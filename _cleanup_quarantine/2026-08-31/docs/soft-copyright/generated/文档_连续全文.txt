## 第一章 软件概述

### 1.1 开发背景

随着大语言模型在客服、办公自动化、知识问答等企业场景的深入应用，业务侧越来越依赖 **Agent（智能体）** 完成多步骤、带工具调用的任务。传统人工抽检无法覆盖回归成本，仅比较最终自然语言答案也难以发现「用错工具、多调工具、中间推理偏离」等问题。

AgentFlow-Eval 针对上述痛点，提供可重复、可追溯、可评分的自动化评测工作台，使研发与测试人员能够以「测试用例」形式固化业务预期，并通过可视化链路与多维分数定位问题。

### 1.2 软件定位

| 项目 | 说明 |
|------|------|
| 软件类型 | 应用软件（Web 前后端分离） |
| 运行形态 | B/S，浏览器访问 |
| 主要用户 | 企业 AI 应用开发者、算法评测人员、质检人员 |
| 部署形态 | 支持单机本地运行与容器化部署，**不强制公网** |

### 1.3 主要功能列表

1. 评测任务的创建、查询、删除、归档与取消  
2. 测试用例批量维护及 CSV/JSON 文件导入  
3. 基于任务队列的异步评测执行（亦支持进程内同步演示模式）  
4. Agent 多轮推理与工具调用执行  
5. 执行轨迹存储与前端 DAG 可视化  
6. 规则评分与 LLM-as-Judge 混合评分  
7. 人工复核覆盖机评结果  
8. 评测报告查看  
9. 系统设置、主题与工作区偏好  
10. API Key 鉴权、租户隔离与审计日志  
11. 实时活动推送（WebSocket）  
12. 内置工具沙箱探测  

### 1.4 技术架构概要

本软件采用前后端分离三层结构：

1. **表现层：** React + TypeScript + Vite + Ant Design + ReactFlow  
2. **业务服务层：** FastAPI 路由、领域服务、Celery 异步任务、Agent 执行器、评分引擎  
3. **数据层：** SQLAlchemy ORM；开发环境 SQLite，完整环境 PostgreSQL；缓存与队列使用 Redis  

数据主路径：

```
用户操作 → REST API →（可选）Celery 任务
    → AgentRunner 执行 → 写入 Trace
    → JudgeEngine 评分 → 写入 MetricScore
    → 报告聚合 → 前端展示
```

### 1.5 独创设计说明（摘要）

本软件独创性主要体现在：评测领域模型与状态机、ReAct 执行与工具沙箱的一体化轨迹记录、规则与 LLM 结合的评分闭环、异步评测编排，以及面向评测人员的可视化工作台，而非对单一开源组件的简单调用堆叠。详见《独创性说明》。

系统划分为以下逻辑子系统：

4. **评判子系统：** 规则指标、LLM 评判、人工复核  
5. **运维支撑子系统：** 配置、日志、审计、种子数据  
6. **前端工作台子系统：** 页面路由、状态管理、可视化组件

### 3.3 关键数据结构

#### 3.3.1 评测任务 Task

包含名称、描述、Agent 配置（模型、温度、最大轮次等）、状态、是否归档、创建者、关联 Celery 任务 ID 等字段。

#### 3.3.2 测试用例 TestSuite

包含用户输入、期望输出、期望工具列表，隶属于某一任务。

#### 3.3.3 执行轨迹 Trace

包含步骤 JSON、状态、token 与费用估算、耗时、各版本号字段，关联测试用例。

#### 3.3.4 指标分 MetricScore

包含指标名称、分数、说明、是否人工覆盖等。

### 3.4 评测执行流程设计

1. 用户创建任务并导入用例。  
2. 用户触发「执行评测」。  
3. 系统将任务置为排队/运行，并投递异步任务（或 Eager 同步执行）。  
4. 对每条用例调用 AgentRunner，得到 steps 与 token 统计。  
5. 持久化 Trace。  
6. 调用评分引擎生成 MetricScore。  
7. 全部用例结束后汇总任务状态，用户在报告页查看。  
8. 可选：对单条轨迹发起重新评判或人工改分。  

### 3.5 安全设计

1. 可选 API Key 鉴权，请求头携带密钥。  
2. 租户隔离：任务按创建者过滤，管理员可全局查看。  
3. CORS 白名单限制浏览器来源。  
4. 接口限流降低滥用风险。  
5. 审计日志记录关键操作。  

### 3.6 界面结构

| 页面 | 功能 |
|------|------|
| 总览 | 任务与活动概览 |
| 任务列表 | 筛选、分页、归档 |
| 创建任务 | 名称与 Agent 参数 |
| 任务详情 | 用例、执行、DAG、日志、评分 |
| 报告 | 聚合结果 |

## 第四章 使用说明（操作要点）

### 4.1 安装与启动（本地 Eager）

1. 安装 Python 3.11+ 与 Node.js 18+。  
2. 后端：创建虚拟环境，安装 `requirements.txt`，复制 `.env.example` 为 `.env`，配置密钥并设置 `CELERY_TASK_ALWAYS_EAGER=true`，启动 uvicorn。  
3. 前端：`npm install` 后 `npm run dev`。  
4. 浏览器访问前端地址，API 文档访问 `/docs`。  
5. 可选执行 `python -m app.core.seed` 导入演示任务。  

### 4.2 安装与启动（Docker）

1. 安装 Docker。  
2. 生成并编辑 `backend/.env.docker`。  
3. 使用 compose 启动 postgres、redis、backend、celery、frontend 等服务。  
4. 浏览器访问宿主机 80 端口（前端）与 8000 端口（API）。  

### 4.3 典型业务操作

1. **创建任务：** 填写名称、模型等参数并保存。  
2. **导入用例：** 在详情页上传 CSV/JSON 或手工批量添加。  
3. **执行评测：** 点击执行，等待状态变为完成/失败。  
4. **查看链路：** 在详情中打开轨迹与 DAG，核对工具调用顺序。  
5. **查看评分：** 阅读各维度分数与说明；必要时人工改分。  
6. **查看报告：** 进入报告页查看汇总。  

### 4.4 演示数据说明

系统提供「客服 Agent 综合评测（Demo）」种子任务，包含天气、计算、机票、邮件、常识五类用例，便于界面展示与流程验证。

# AgentFlow-Eval 软件设计说明书

## 1. 引言

### 1.1 项目背景

AgentFlow-Eval 是一个面向企业 AI 应用开发者的 Agent 自动化评测工作台。随着大语言模型（LLM）在企业场景中的广泛应用，如何系统性地评估 AI Agent 在执行业务任务时的表现成为一个关键需求。本项目提供了一套完整的评测流水线：上传业务测试用例 -> 自动运行 Agent -> 可视化展示执行链路 -> 生成评测报告。

### 1.2 项目目标

- 提供可视化 Agent 执行链路追踪（基于 ReactFlow 的 DAG 图）
- 支持自定义业务指标打分（基于 LLM-as-Judge 的多维度评分引擎）
- 支持异步任务队列（基于 Celery + Redis）
- 通过 CSV/JSON 文件批量导入测试用例
- 生成结构化的评测报告，包含各维度分数分布和详细扣分说明

### 3.3 核心算法

#### a. OpenAIReActRunner（多轮 ReAct 循环执行器）

**文件**: `backend/app/core/agent_runner/openai_runner.py`

**设计思路**:
实现完整的 ReAct（Reasoning + Acting）循环，让 LLM 能够迭代推理、调用工具、观察结果，直到得出最终答案。

**执行流程**:

```
用户 Query
   │
   ▼
┌──────────────────────────────────────────────────────────────┐
│                    ReAct Loop (max_iterations=5)              │
│                                                              │
│  ┌─────────┐     ┌──────────┐     ┌───────────┐             │
│  │ Thought  │────→│  Action  │────→│Observation│             │
│  │ (推理)   │     │ (行动)   │     │ (观察)    │             │
│  └─────────┘     └──────────┘     └───────────┘             │
│       │               │                │                    │
│       │        ┌──────┴───────┐        │                    │
│       │        │              │        │                    │
│       │   ┌──────────┐ ┌───────────┐  │                    │
│       │   │工具函数  │ │最终答案   │  │                    │
│       │   │执行      │ │final_answer│  │                    │
│       │   └──────────┘ └─────┬─────┘  │                    │
│       │                      │        │                    │
│       └──────────────────────┘────────┘                    │
│                              │                             │
│                              ▼                             │
│                        最终答案                             │
└──────────────────────────────────────────────────────────────┘
```

**两种执行模式**:

1. **函数调用模式**（默认）：使用 OpenAI 原生 tool_calls API。LLM 返回结构化工具调用指令，系统执行对应函数并将结果作为 tool response 消息送回。

2. **文本解析模式**（回退）：当 LLM 未使用函数调用格式时，解析其文本输出中的 Thought/Action/Action Input 标签。支持中英文标签。

**工具执行**:

```python
class ToolDefinition:
    name: str           # 工具名
    description: str    # 描述
    parameters: dict    # JSON Schema
    fn: Callable | None # 可选的可调用实现
```

- 当 `fn` 提供时：直接调用 `fn(**args)` 并返回结果字符串
- 内置模拟：`web_search` 和 `calculator` 两个默认实现
- `calculator` 使用 `ast.parse` 安全计算数学表达式

**返回结构**:

```python
{
    "steps": [
        {"iteration": 0, "thought": "分析...", "action": "search", "action_input": "...", "observation": "...", "tokens": 50},
        {"iteration": 1, "thought": "完成", "action": "final_answer", "action_input": "答案是...", "observation": "", "tokens": 30}
    ],
    "total_tokens": 80,
    "iterations": 2,
    "final_answer": "答案是...",
    "status": "success" | "failed" | "max_iterations_reached",
    "response_time_ms": 1234
}
```

---

#### b. LLMJudge（两阶段混合评分引擎）

**文件**: `backend/app/core/judge_engine/llm_judge.py`

**设计思路**:
创新性地将规则基评分与 LLM 深度语义分析相结合，实现两阶段混合评分流水线。第一阶段运行无 LLM 依赖的快速规则评分，第二阶段启用 LLM 进行语义级精化。

**评分流水线**:

```
evaluate(trace_steps, expected_output, expected_tools?)
                       │
                       ▼
┌────────────────────────────────────┐
│      Stage 1: Rule-based          │ ← 始终运行，零外部依赖
│      Pre-scoring                  │
│                                    │
│  ┌──────────────────┐              │
│  │ tool_accuracy     │ 集合匹配     │
│  │ (0-40)           │ 缺/多工具扣分 │
│  └──────────────────┘              │
│  ┌──────────────────┐              │
│  │ answer_correctness│ 词汇重叠率   │
│  │ (0-40)           │ ×40           │
│  └──────────────────┘              │
│  ┌──────────────────┐              │
│  │ reasoning_coherence│ 重复检测    │
│  │ (0-20)           │ 迭代计数     │
│  └──────────────────┘              │
└──────────────┬─────────────────────┘
               │
               ▼ (when API key available)
┌────────────────────────────────────┐
│      Stage 2: LLM-as-Judge        │ ← 可选，需要 API Key
│      Refinement                    │
│                                    │
│  发送 Trace + 预评分结果给 LLM       │
│  LLM 输出多维度的精细分数和理由       │
│  可以是配或调整预评分                  │
└────────────────────────────────────┘
               │
               ▼
        返回结构化评分结果
```

**评分维度与权重**:

| 维度 | 权重 | 规则评分方法 | LLM 精化 |
|------|------|-------------|----------|
| tool_accuracy | 40分 | `calc_tool_accuracy()` 集合精确匹配，每个缺失/多余工具扣 10 分 | LLM 分析参数正确性和调用上下文 |
| answer_correctness | 40分 | 词汇重叠率 × 40，基于期望输出与提取答案的单词交集比 | LLM 语义级判断，处理同义词和改写 |
| reasoning_coherence | 20分 | 重复思考检测(每次 -4)，迭代过多(超 8 次扣分) | LLM 评估逻辑连贯性和推理质量 |

**混合模式行为**:

- 有 API Key → `_llm_refine()` 发送预评分 + Trace 给 LLM，LLM 返回精化后的 JSON 评分
- 无 API Key → 跳过 LLM 阶段，直接返回规则评分，设置 `mode: "rule_only"`
- LLM 调用失败 → 回退到规则评分，记录错误信息

**缓存机制**:
- 使用 `dict` 实现简单 LRU 缓存（max 128 条）
- 基于输入参数的 SHA256 哈希作为缓存键
- 相同输入直接返回缓存结果，避免重复 LLM 调用

**输出 `dict` 结构**:
```python
{
    "scores": {"tool_accuracy": 40.0, "answer_correctness": 32.0, "reasoning_coherence": 16.0},
    "total": 88.0,
    "reason": "[Rule-based] Tool: ... | Answer: ... | Coherence: ...",
    "token_cost": 0,
    "mode": "rule_only" | "hybrid",
    "details": {
        "tool_accuracy": {"score": 40.0, "reason": "...", "expected": [...], "actual": [...]},
        "answer_correctness": {"score": 32.0, "reason": "...", "extracted_answer": "..."},
        "reasoning_coherence": {"score": 16.0, "reason": "...", "iteration_count": 3}
    },
    "step_analysis": [
        {"index": 0, "has_thought": true, "has_action": true, "action_name": "web_search", "is_expected": true},
        {"index": 1, "has_thought": true, "has_action": true, "action_name": "final_answer", "is_expected": None}
    ]
}
```

### 3.5 异步任务层

**文件**: `backend/app/core/celery_app/tasks.py`

**三个 Celery 任务**:

```python
# 子任务 1: 执行测试用例
@celery_app.task(bind=True, max_retries=2)
def run_single_test_suite(self, test_suite_id: str, agent_config: dict) -> dict

# 子任务 2: 评分 Trace
@celery_app.task(bind=True, max_retries=2)
def run_judge_evaluation(self, trace_id: str, expected_output: str, expected_tools: list) -> dict

# 编排任务: 完整流水线
@celery_app.task(bind=True)
def run_full_evaluation(self, task_id: str) -> dict
```

**评测流水线**:

```
run_full_evaluation(task_id)
  ├── 1. 加载 Task + TestSuites
  ├── 2. 状态 → running
  ├── 3. Celery group: 并行执行所有 suites
  │     └── run_single_test_suite
  │           ├── OpenAIReActRunner.run()
  │           └── 持久化 Trace
  ├── 4. Celery group: 并行评分所有 traces
  │     └── run_judge_evaluation
  │           ├── LLMJudge.evaluate()
  │           └── 持久化 MetricScore
  ├── 5. 汇总：平均分 + 各维度分数
  └── 6. 状态 → completed | partial | failed
```

**错误隔离**: 每个子任务包裹 try/except，单个用例失败不影响其他用例执行。

## 7. 安全性设计

### 7.1 API Key 管理

- OpenAI API Key 通过环境变量 `OPENAI_API_KEY` 注入
- LLMJudge 自动检测 API Key：有则启用混合评分，无则纯规则评分
- 后端启动时不验证 API Key 有效性，避免启动失败

### 7.2 CORS 配置

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["http://localhost:5173"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

- 仅允许开发环境前端地址跨域访问
- 生产环境需替换为实际部署域名

### 7.3 输入验证

- 所有用户输入通过 Pydantic 模型验证
- SQLAlchemy ORM 防止 SQL 注入
- 禁止直接拼接 SQL 或 Shell 命令
- CSV/JSON 文件解析在前端完成，后端仅接收已验证的结构化数据

### 7.4 数据库安全

- 开发环境使用 SQLite，生产环境使用 PostgreSQL
- ORM 参数化查询防止注入
- 外键使用 CASCADE 删除确保数据完整性

右侧「Scoring Results」卡片显示：
- 仪表盘总分（环形进度条）
- 各维度分数字段（tool_accuracy/answer_correctness/reasoning_coherence）
- 评分说明（扣分/加分理由）

### 3.5 步骤日志

「Step Log」面板以时间线形式展示每个 ReAct 步骤的详细内容：
- 步骤类型标签（颜色编码与链路图一致）
- 工具名称和输入参数
- 完整执行内容（超过 200 字符自动截断）

## 4. 解读评分报告

### 4.1 三个评分维度

#### 工具调用准确率（满分 40 分）

评估 Agent 是否正确调用了预期工具。评分规则：

| 扣分项 | 扣分 |
|--------|------|
| 缺少一个必要工具 | -10 分 |
| 使用了预期外的工具 | -10 分 |
| 工具参数明显错误 | -5 分/次 |

#### 答案准确性（满分 40 分）

评估 Agent 的最终回答是否包含预期输出的核心信息。评分规则：

| 扣分项 | 扣分 |
|--------|------|
| 遗漏核心信息 | -15 分 |
| 信息不准确 | -10 分 |
| 回答过于笼统 | -5 分 |

#### 推理链路合理性（满分 20 分）

评估 Agent 的思考过程是否合理。评分规则：

| 扣分项 | 扣分 |
|--------|------|
| 明显的重复思考 | -8 分 |
| 逻辑跳跃或错误推理 | -6 分 |
| 步骤冗余 | -4 分 |

### 4.2 总分计算

```
总分 = tool_accuracy(0-40) + answer_correctness(0-40) + reasoning_coherence(0-20)
     = 0-100 分
```

**评分说明**：
- 无 LLM API Key 时：纯规则评分，返回 `mode: "rule_only"`
- 有 LLM API Key 时：规则 + LLM 混合评分，返回 `mode: "hybrid"`
- LLM 评分失败时：自动回退到规则评分

### 4.3 报告导出

在评测详情页顶部可查看完整的聚合报告，包含：
- 测试用例总数、成功/失败数
- 各维度平均分
- Token 消耗和耗时统计
- 每个测试用例的详细执行结果

## 5. 常见问题 FAQ

### Q1: 前端启动后页面空白怎么办？

1. 确认已执行 `npm install` 安装依赖
2. 检查控制台是否有报错信息
3. 确认 Node.js 版本 ≥ 18
4. 尝试清除 `node_modules` 后重新安装

### Q2: 后端启动报错 ModuleNotFoundError？

```bash
# 确认已安装所有依赖
pip install -r requirements.txt

# 确认在正确的目录下执行
cd AgentFlow-Eval/backend
```

### Q3: 评测任务执行失败？

1. 确认已设置有效的 `OPENAI_API_KEY`
2. 检查测试用例格式是否正确
3. 查看后端日志 `logs/agentflow_eval.log` 获取详细错误信息
4. 确认 Redis 服务已启动（如果使用 Celery 模式）

### Q4: 没有 OpenAI API Key 能否使用？

可以。系统会自动检测 API Key：
- 有 Key：启用混合评分模式（规则 + LLM）
- 无 Key：启用纯规则评分模式（工具准确率 + 词汇重叠 + 推理启发式）

Agent 执行需要 API Key；评分引擎可以在无 Key 模式下运行。

### Q5: 上传 CSV/JSON 时提示格式错误？

**CSV 格式要求**：
- 第一行必须为列头：`query,expected_output,expected_tools`
- `query` 列为必填
- 如果字段值包含逗号，请用双引号包裹：`"value,with,commas"`

**JSON 格式要求**：
- 必须是数组：`[...]`
- 每个元素必须包含 `"query"` 或 `"user_query"` 字段

### Q6: 如何重置数据库？

删除项目根目录下的 `agentflow_eval.db` 文件，重启后端服务即可自动重建。

### Q7: 支持哪些语言？

目前 Agent 提示词和 LLM 评分提示词支持中文和英文。前端界面使用英文标签，但包含中文字符注释。

# AgentFlow-Eval 软件独创性说明

**软件全称：** AgentFlow-Eval Agent 自动化评测工作台  
**版本号：** V1.0  
**开发方式：** 独立开发  
**说明用途：** 计算机软件著作权登记申请 — 独创性与鉴别说明  

---

## 1. 软件概述

本软件是面向企业 AI 应用场景的 **Agent（智能体）自动化评测工作台**。用户可创建评测任务、导入业务测试用例，系统自动调度 Agent 执行，记录完整推理与工具调用轨迹，并结合规则指标与大模型评审（LLM-as-Judge）生成多维评分与结构化报告。

与通用聊天 Demo 或单一 API 封装不同，本软件形成了「用例管理 → 异步执行 → 轨迹可视化 → 混合评分 → 报告与审计」的 **端到端评测闭环**，具有独立的数据处理流程与界面交互设计。

---

## 2. 独创性要点（相对通用框架的差异化）

### 2.1 评测领域数据模型与状态机

- 自定义 **Task / TestSuite / Trace / MetricScore / AuditLog** 领域模型及任务状态迁移（创建、排队、运行、完成、失败、取消、归档）。
- Trace 中结构化保存 ReAct 步骤、token、耗时及版本元数据（agent/prompt/model/tool version），支撑评测可追溯。

### 2.2 Agent 执行与工具沙箱一体化

- 抽象 `BaseAgentRunner`，实现 OpenAI 兼容 **ReAct 多轮执行器**。
- 内置 **工具沙箱**（超时控制、工具列表探测），将工具调用结果写回轨迹，而非仅保存最终自然语言回复。

### 2.3 混合评分引擎（规则 + LLM-as-Judge + 人工复核）

- `metrics` 模块实现无 LLM 的轻量规则分（如工具集合准确率、答案抽取）。
- `LLMJudge` 在规则分基础上调用大模型进行多维语义评分并生成扣分说明。
- 支持 **人工审核覆盖评分**，形成机评与人评结合的质检流程。

### 2.4 异步评测流水线

- 基于 Celery + Redis 的 `run_full_evaluation` 全流程任务：逐条执行用例、落库轨迹、自动评判、更新任务状态。
- 支持 Eager 模式（进程内同步）便于单机演示，与生产异步模式共用业务代码路径。

### 2.5 可视化与前端工作台

- 基于 ReactFlow 的 **执行链路 DAG 可视化**、步骤日志与评分卡片联动。
- 任务创建、用例上传、报告浏览、主题与工作区设置等完整 Web 交互，非命令行脚本集合。

### 2.6 企业级横切能力

- API Key 鉴权、基于 actor 的租户数据隔离、审计日志、接口限流、WebSocket 活动推送等，构成可落地的评测工作台形态。
